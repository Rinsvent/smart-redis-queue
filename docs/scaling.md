# Масштабирование через Redis

Отдельного кластера «брокеров SRQ» нет. Масштаб — это Redis и число клиентов. Для очереди задач на Redis так и задумано.

## Что реально помогает

1. **Больше consumer’ов** — unordered-партиции и разные группы утилизируются параллельно.
2. **Шардинг по нескольким Redis** — явный список `{addr, db}`, sticky ByGroup / ByManual. См. [Шардинг](sharding.md).
3. **Несколько Redis DB на одном процессе** — изоляция namespace, **не** ускорение Lua.
4. **Меньше горячих ключей** — короткие блоки, rate limit на Get, `BlockGroups` вместо шторма Reject, `race!` только там, где нужен.

Redis Cluster для SRQ пока не поддерживается (ключи одной очереди должны быть вместе).

## Паркуйте группу, не каждую партицию

При лимите на аккаунт:

```go
return redisqueue.NewRejectWithDelay(err, 2.0, "acct:9f3a")
```

Иначе Get продолжит обходить O(N) партиций, и нагрузка на Redis вырастет вместе с их числом.

С `BlockGroups` простой Get по запаркованной группе почти не зависит от N. См. [Бенчмарки](benchmarks.md).

## Multi-tenant

| Уровень | Как обычно делают |
|---------|-------------------|
| Логический | разные имена `queue` |
| Redis | отдельная DB или отдельный инстанс на tenant |
| Квоты | rate limit и backpressure по group / tag |
| Ops | Redis ACL и фильтры в UI |

Отдельного SaaS-tenant слоя в протоколе пока нет — см. [Roadmap](roadmap.md).

## Чего ждать не стоит

- Масштаба «как у Kafka, но без общего Redis».
- Fan-out как способа размазать одно событие по многим воркерам.

Для роста throughput смотрите topology Redis и правильную парковку групп.
