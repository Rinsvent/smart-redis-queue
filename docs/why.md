# Зачем Smart Redis Queue

## Обычная история

В проекте уже есть Redis — кэш, сессии, локи. Потом появляются фоновые задачи: что-то нужно делать по порядку и не превышать лимиты внешнего API. Часто в этот момент поднимают Kafka или RabbitMQ.

Иногда так и надо. Но нередко получается лишний кластер: мониторинг, ACL, релизы — а rate limit и «оставить только последний payload» всё равно пишутся в приложении. Redis при этом уже стоит рядом.

SRQ остаётся очередью задач на Redis. Ack, reclaim, порядок — как у нормальной очереди; то, ради чего обычно городят middleware вокруг брокера, уже встроено.

## Чем не хватает «просто Redis»

| Подход | Чего обычно не хватает |
|--------|------------------------|
| Lists (`LPUSH` / `BRPOP`) | Порядок по ключу, priority, delayed, возврат задач после смерти воркера |
| Streams | Двойной rate limit (аккаунт + ресурс), debounce, mutex между партициями |
| Свой набор Lua | Стабильный API, UI, нормальные тесты |

SRQ даёт готовую модель ключей, Lua, Go API и инструменты для ops.

## Почему не Kafka

Kafka сильна как лог событий: replay, fan-out, свой кластер брокеров.

У SRQ другая задача:

| | Kafka | SRQ |
|--|:-----:|:---:|
| Модель | Append log | Очередь задач (Get → Ack) |
| Replay | Да | Пока нет (в планах — журнал) |
| Fan-out | Да | Нет (одну задачу берёт один воркер) |
| Priority / delayed | Слабо / руками | Да |
| Rate limit на стороне выдачи | Нет | Да (несколько алгоритмов) |
| Debounce «всегда последний payload» | Нет | `deb!` |
| Mutex между партициями | Нет | `race!` |
| Масштаб | Брокеры Kafka | То, как развёрнут Redis |

Если нужен event bus и долгий аудит-лог — берите Kafka или аналог. Если нужна очередь задач рядом с уже живым Redis — SRQ.

## Почему не RabbitMQ

Rabbit хорошо закрывает durable queues, priority, delayed (часто через плагины), prefetch.

Чего обычно нет сразу:

- rate limit на выдаче сразу по двум осям (аккаунт и ресурс);
- debounce с перезаписью payload;
- mutex ресурса между партициями (`race!`);
- окно «тот же ID после успешного Ack больше не принимать».

При этом появляется AMQP-кластер, хотя Redis уже умеет похожие вещи.

## Когда Redis достаточно

Практичное правило:

1. Redis уже в проде — начните с очереди на нём.
2. Нужны порядок, лимиты API и debounce — SRQ это закрывает без второго брокера.
3. Нужен долгоживущий лог и много независимых подписчиков — это уже другой класс систем.

Масштаб SRQ — это масштаб Redis: несколько DB, несколько инстансов, Cluster (если аккуратно с ключами для Lua). «Kafka масштабируется без общего Redis» — про другую архитектуру, не аргумент против очереди на Redis.

## Типичные кейсы

**Внешний API с квотами.** Воркеры ходят в HTTP API: лимит на аккаунт и более жёсткий порядок/лимит на ресурс (заказ, документ, ящик). Партиция `!{account}:{resource}`, группа `acct:{account}`. Упёрлись в MAX аккаунта — паркуете группу, а не тысячи ресурсов по отдельности.

**Много ключей со строгим порядком.** Нужен порядок по каждому заказу/документу, а ключей тысячи или десятки тысяч. В Kafka и RabbitMQ это упирается в физические партиции/очереди и head-of-line между чужими ключами. В SRQ каждая `!`-партиция независима, число воркеров от числа ключей не зависит. Разбор: [Сравнение — много логических ключей](comparison.md#many-ordered-keys).
