# FAQ

## SRQ заменяет Kafka?

Нет. Kafka — лог событий, replay и fan-out. SRQ — очередь задач на Redis с порядком и rate limit. См. [Зачем SRQ](why.md) и [Сравнение](comparison.md).

## Нужен ли отдельный Redis только под очередь?

Не обязательно. Часто используют тот же инстанс, что и для кэша. При высокой нагрузке — отдельный Redis или [шардинг](sharding.md). Несколько DB на одном процессе не дают параллельный Lua, но уменьшают число ключей в одной DB (возможен небольшой прирост). Кратное ускорение Lua — от нескольких процессов Redis.

## Как добавить шард без потери задач?

Сначала consumer’ы слушают новый шард; write-remap без drain опасен. Для снятия шарда — `ReadOnly`, дождаться пустой очереди, потом убрать из конфига. Пошагово в [Шардинге](sharding.md#добавление-и-удаление-шарда).

## At-least-once значит возможны дубли?

Да. Делайте handler идемпотентным и/или включите [idempotency TTL](features/debounce-idempotency.md).

## Publish вернул OK — сообщение точно на диске?

Только если Redis так настроен. Без AOF/`appendfsync always` (или надёжной реплики) `kill -9` / power loss может стереть уже «успешный» Publish. Подробности и цифры — [Гарантии доставки](delivery.md#персист-redis-что-гарантирует-srq-что--redis).

## Чем rate limit группы отличается от backpressure по тегу?

| | Rate limit / BlockGroups | Tag backpressure |
|--|--------------------------|------------------|
| Когда | При выдаче или после 429 | При Publish |
| Что режет | Скорость обработки | Глубину очереди |
| Scope | group / partition | tag |

## Можно ли несколько групп на задачу?

Да, но для типового лимита API хватает одной группы на аккаунт. Несколько групп усложняют обход ready.

## Desktop и server — один бинарь?

Нет. Desktop собирается с `-tags wails` (на Linux ещё GTK). Server — с `-tags server`, без CGO. См. [Приложения](apps.md).
