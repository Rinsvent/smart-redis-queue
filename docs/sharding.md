# Шардинг

SRQ умеет раскладывать одну логическую очередь по нескольким standalone Redis (`addr` + `db`). Так получают **параллельные Lua**-исполнители: у каждого процесса Redis свой main thread.

Redis Cluster в этом релизе **не поддерживается**: ключи одной очереди должны жить вместе (группы, партиции, rate limit, `race!`).

## Когда нужен

| Цель | Что делать |
|------|------------|
| ×N throughput Lua | N отдельных `redis-server` (порты / контейнеры), не N DB на одном процессе |
| Изоляция namespace | Разные DB на одном Redis — ок, но **без** ускорения Lua |
| Несколько независимых очередей | `ShardByQueue` или явный `KeyMap` |

Несколько logical DB (`SELECT 0…15`) на **одном** процессе не дают параллельных `EVAL`: скрипты всё равно идут в одну очередь main thread.

## Конфиг

```go
cfg := &redisqueue.ShardConfig{
    Strategy: redisqueue.ShardByGroup, // см. стратегии ниже
    Shards: []redisqueue.Shard{
        {Name: "s0", Addr: "127.0.0.1:6379", DB: 0},
        {Name: "s1", Addr: "127.0.0.1:6380", DB: 0},
        {Name: "s2", Addr: "127.0.0.1:6381", DB: 0},
    },
}

producer := redisqueue.NewProducer(nil, "demo-mail")
if err := producer.SetShards(cfg); err != nil { /* ... */ }
defer producer.Close()

pool := redisqueue.NewConsumerPool(nil, "demo-mail")
if err := pool.SetShards(cfg); err != nil { /* ... */ }
defer pool.Close()
pool.SetCount(12) // суммарно; делятся по шардам
pool.Consume(ctx, handler)
```

Список шардов — **явный**: разные хосты/порты (и при необходимости `DB`). Для ×N Lua важны разные процессы (`Addr`), не разные DB.

Опционально: готовый `Client` в `Shard`, веса (`Weight`), sticky-таблица `KeyMap` (ключ → имя шарда).

## Стратегии

Один *shard key* всегда должен попадать на один и тот же шард — иначе ломаются `BlockGroups`, group rate limit и `race!`.

| Стратегия | Ключ шарда | Когда |
|-----------|------------|--------|
| `ShardByGroup` | `Groups[0]` (пусто → `_default`) | Много аккаунтов / ключей API; **рекомендуемый default** |
| `ShardByQueue` | имя очереди | Несколько независимых очередей на общем router |
| `ShardByManual` | строка из `WithShardKey` / `PublishManual` | Сами решаете: очередь, партиция, tenant id… |
| `ShardByPartition` | `Task.Partition` | Только если **не** нужны group RL / `BlockGroups` / `race!` между партициями одной group |

`ShardByManual` — когда формула «группа» или «очередь» не подходит: передаёте произвольную строку, router считает `hash(key) % N` (с учётом весов и `KeyMap`).

При нескольких `Groups` шард берётся от первой; для ByGroup лучше одна group на задачу. Опция `StrictSingleGroup` — ошибка Publish, если групп больше одной.

## Producer и consumer

- Тот же `Producer` / `ConsumerPool`: `SetShards(cfg)` (клиент из `New*` после этого не нужен).
- Producer и pool обязаны использовать **один и тот же** `ShardConfig`.
- Pool слушает **все** шарды; `SetCount` — сумма воркеров, они делятся по шардам.
- Батч Publish режется по шардам (в одном Lua нельзя смешивать разные Redis).
- Явный пин: `PublishTo(ctx, "s1", tasks...)` / `PublishManual` / `WithShardKey`.
- Rate limit и `BlockGroups` — **per-shard** (при sticky ByGroup один аккаунт всегда на одном шарде — этого достаточно).

## Добавление и удаление шарда

Смена числа шардов при `hash % N` **переназначает** часть ключей. Живые задачи сами не переезжают. Без процедуры возможны «тихие» хвосты на старом шарде и дубли ID на новом.

### Добавить шард (безопасно)

1. Поднять новый Redis, добавить его в конфиг consumer’ов и **перезапустить воркеры** (они начнут слушать новый шард).
2. Пока очередь не пустая / не готова к remap — **не** меняйте число шардов для write-маршрутизации «вслепую».
3. Практичные варианты без миграции данных:
   - новый шард только для **новых** ключей через `KeyMap` / `ShardByManual` + явные ключи;
   - или завести **новую** очередь / новый набор имён групп на расширенном конфиге;
   - полный remap — только после **drain** старых ключей (ниже).

Автоматического rebalance ключей в v1 нет.

### Убрать шард (drain)

1. Пометить шард `ReadOnly: true` в общем конфиге (продюсеры на него больше не пишут).
2. Перезапустить **продюсеры**, затем убедиться, что consumer’ы всё ещё слушают этот шард (он остаётся в списке).
3. Дождаться нулевой глубины на шарде (UI / `Admin` / метрики).
4. Убрать шард из конфига и перезапустить consumer’ов.

Пока шард в конфиге с `ReadOnly: true`, воркеры продолжают его обрабатывать сами — отдельно «объяснять» им drain не нужно, достаточно общего конфига и рестарта после смены флага.

### Чего не делать

- Удалять шард из конфига consumer’ов, пока на нём есть задачи.
- Менять `Strategy` или формулу hash при непустых шардах без drain.
- Публиковать тем же `Task.ID` на другой шард, пока старый payload жив — это две независимые записи.

## Ограничения

- Не Redis Cluster.
- Лимиты Get — на каждом шарде свои счётчики.
- Admin/Desktop: смотрите каждый `addr` (и DB) из списка шардов.
